—How to read this, and the words we use

This is a decision log. Every section records four things in the same order: what we do, other choices, why not those, and the proof — the number that decided it. Every figure was measured on real catalogue data. Nothing is a guess.

The one rule for anyone changing this app

If you change a decision here, measure it first, then update this document and README.md together. The numbers are the reason, not somebody's opinion.

Precision — out of all the warnings we show, how many were correct. High precision means we rarely cry wolf. This is the number that matters most.

Recall — out of all the real duplicates that exist, how many we actually found. High recall means we miss very little.

Separation — how much more often a field agrees in real duplicates than in non-duplicates. A field that agrees 90% of the time in both cases tells you nothing; only the gap counts.

Ablation — take one piece away and see whether the system gets worse. If nothing changes, that piece was not earning its place.

Veto gate — our safety rules. After scoring they can cancel a match outright, no matter how alike the two names looked.

Label leakage — when a learning model is accidentally shown the answer. It scores beautifully in testing and fails completely in real use.

Cat No — the manufacturer's own catalogue number. Two items sharing one are almost always the same product.

Rare-word index — for every item we store its 4 rarest words, so a new name can be matched against only the items that share one.

0The big one: search, or machine learning?

What we do. A search system first; a model added later as one small part of it. Find candidates → score them → safety rules decide → and only then does a model improve the scoring.

Why not a model first. A model takes two items and compares them. It cannot go and find the second item. With 22,204 items there are about 246 million possible pairs — you cannot run a model on all of them. Something must shortlist first, and that something is the search. A model also needs examples, and at the start we had none.

Why not an AI for everything. Too slow (1–3 seconds), costs money per check, and needs internet from the server. Kept as an optional helper for hard cases only.

Proof — group-wise split, 18 clues, 8,614 held-out test pairs:

Hand-written rules    precision 75.7%    recall 49.2%
Trained model         precision 76.3%    recall 50.4%
                      the model added +1.2 points

Almost all the value sits in the search and the safety rules. That is why the model comes last. One nice detail: the model independently rediscovered our hand-written length penalty (section 5) straight from the data.

1A separate app, not code inside another app

What we do. A standalone Frappe app, item_duplicate_check.

  • Not inside another app — you could not switch it off on its own. If it misbehaves during live item creation you need to disable one thing, fast.
  • Not a Server Script — several code files, cached data, background jobs, unit tests and later a model file do not fit in a script box, and cannot be tested.
  • Not an edit to ERPNext's Item — breaks on the next upgrade. This app only adds hooks and new doctypes; core Item is untouched.

Proof. Three custom fields (custom_item_creation_reference, custom_item_creation_type, custom_category) still sit on Item holding data, but the app that created them was removed and their link targets are gone. That is exactly the mess a clean, removable app avoids.

2Cleaning up the text

What we do. Before comparing two names we clean both the same way. Ten rules, and the order is locked — several only work if an earlier one has already run. Rule 2 before rule 3, rule 1 before rule 5, rule 7 before rule 9.

Why not compare names as typed? 12% carry a ™ on their own and would never match. Why keep digits? Removing them destroys the sizes the safety rules need. Why no spell-checker? Scientific names are not dictionary words; it would corrupt them.

Why we rejected sound-alike matching (Soundex, Metaphone). They code a word by how it sounds, and were designed for English surnames. Over PmeI, Axygen, 2-Mercaptoethanol they produce near-random matches. The one case they would have helped — DNase vs DNAse — is already solved by lower-casing. They would add wrong answers and find nothing new.

3The safety rules — the veto gate

This is the most important part of the app. More accuracy comes from this one file than from everything else combined. After scoring we ask whether the two items are actually different products wearing similar names. If so the match is cancelled — score forced to zero — no matter how alike the text was.

#CheckThe rule
1SizeConvert to a base unit and compare, so 1kg = 1000g. Disagreement on a shared measurement → cancel.
2Number codesAny word containing a number. Both sides have one and they differ → cancel.
3Negationno, without, non, free, reduced, anti → cancel if they differ.
4Gradeabsolute, HPLC, sterile, RNase free, 70% → cancel if they differ.

The pattern behind the whole design

The detail that tells two products apart is almost always a word containing a number, or a negation word. That single observation is the entire design of this module.

Proof

Version of the gatePrecisionRecall
No gate78.1%88.5%
Size and grade only81.4%89.7%

The full gate trades 10 points of recall for 10 of precision. We take that trade: a wrong warning costs user trust permanently, a missed duplicate costs one extra row.

Why not let the model learn it? We tested that. The model gave a size conflict a weight of only −0.23 — it treats an absolute rule as a mild preference. A hard rule is far better.

The rule for maintaining this file

Every false warning seen in production becomes a test case in tests/test_specs.py first, then the rule is fixed. Never patch a rule without leaving a test behind. That file is the living rulebook.

4How we find items worth comparing

What we do. A rare-word index. For every item we store its 4 rarest words; to find candidates for a new name we look up its rare words and collect the items that share them. Nunc, Axygen and PmeI point straight at the right items; plate, tips and sterile are ignored for lookup.

MethodFound in top 5Speed
Item Child Group filter24.7%48.5 ms
Rare-word index  — chosen89.7%4.7 ms
Scan the whole catalogue89.8%24.9 ms

The number that changed the plan

Narrowing by Item Child Group was our original design, and it failed badly: 80.5% of real duplicate pairs sit in different child groups, because the teams that created the duplicates also filed them under different categories. The model could have been perfect and the system would still have missed 3 out of 4 duplicates — the right item never reached it.

A vector database is unnecessary at this size; exact comparison is cheaper than the infrastructure. Fallback: a name with fewer than 2 usable words falls back to the full scan, and 24.9 ms is still well inside budget.

5How we score a pair

score = safety gate x (  0.47  how alike the words are, in order
                       + 0.21  how alike the word sets are, x length penalty
                       + 0.18  how many rare words they share
                       + 0.14  do the fields agree (manufacturer) )

The safety gate is 0 or 1.  A 0 cancels everything.
An exact Cat No match jumps straight to 0.97 and skips the weights.

Why hand-written and not a model. It can be explained — the panel says "names 96% alike, same manufacturer, both 50 ml" instead of "0.94", and people trust a tool that explains itself. It can be tuned without retraining, since every weight is a setting. And it works on day one with no training data.

The length penalty — do not remove it. The standard word-set score gives a perfect 100 whenever one name's words are all contained in the other's:

100   "DNase I, RNase-free (1 U/uL)"   vs   "DNAse"
100   "PmeI, recombinant"              vs   "PmeI"
100   "Plasmid DNA - qwp"              vs   "Plasmid DNA"

Multiplying by shortest / longest fixes it. When we trained the model it learned this same correction by itself — independent confirmation the rule is right.

Why rare-word overlap gets 0.18. Two items sharing nunc is strong evidence; two items sharing plate is almost none. Plain string similarity cannot tell the difference, so we weight each shared word by how rare it is.

6Cat No is a lookup, not a clue

What we do. Cat No is used in Step 0 as a direct lookup — same Cat No, return that answer at once with high confidence. It is never handed to the scorer or the model as a clue.

Why this matters. Our only source of training examples is "these two share a Cat No, so they are the same product". If the model also sees Cat No as a clue it learns one useless rule — same Cat No means same item — and learns nothing about names. It would test beautifully and fail on the 31% of items with no Cat No. That mistake is label leakage. Keeping the two jobs apart also makes our accuracy figures honest: we measure the scorer against Cat No, which is fair precisely because the scorer never sees it.

Proof it works as a key. 10,500 Cat No values in use; 3,319 are already shared by more than one item, covering 7,781 items (35% of the catalogue); 8 groups checked by hand at random were all genuine duplicates.

Two cautions

A Cat No match is evidence, not proof — the safety rules still apply on top. Real example: cat=SUFR38200 covers both "Tyvek roll Flat reels-38 cm" and "…40cm x 200 mtr".

Clean the junk first. 320 items use placeholders (0 ×172, na ×144). The 172 items sharing "0" alone produce 14,706 phantom pairs. Removing junk takes 24,569 raw pairs down to 5,473 real ones. That is the difference between good training data and poisoned training data.

8The machine learning model, and its training data

What we do. A pair classifier — give it two items, it returns the chance they are the same. It replaces only the scoring function from section 5, and only if it beats the hand-written weights on data it has never seen. Main model: Logistic Regression (right size for ~20 clues and a few thousand examples, trains in under a second, and the weights are readable). Challenger: Gradient Boosting, trained purely for comparison.

RejectedWhy
Neural networkFar too little data; no benefit at this size
Random Forest / SVMNo real gain here, and harder to explain
Embeddings as the main judgeThey rate Glycine 500g and Glycine 1kg as about 97% the same — actively dangerous on this catalogue. Kept as a possible extra later, behind the safety rules, small weight.
Fine-tuning our own embedding model3–5 weeks, needs a GPU and thousands of clean labels. Revisit in a year.

Honest expectation: +1.2 points over good rules. Not 15. Today's examples come from Cat No agreement, and those are easy pairs — mostly near-identical names, with little for a model to learn. The real gain comes later from the production log, where the examples are hard cases a human had to think about. Expect +6 to +8 points there.

Source of examplesGives usWhen
Items sharing a Cat No, junk removed5,473 duplicate pairs — 8 of 8 checked by hand were realNow
Hard non-duplicates from our own search592,497 available, ~21,900 neededNow

Why non-duplicates must come from our own search. If the model trains on easy pairs but the live system shows it hard ones, it fails in real use. Training and live scoring must see the same kind of pair.

The rule

Ship the hand-written weights unless the model clearly wins on the expert test set. Ties go to the simpler option. Keep the hand-written scorer in the code permanently, as an automatic fallback if the model file is missing or fails to load.

9What the user sees, and never blocking a save

ScoreMessageWhat they can do
0.92 and above"This item looks like it already exists", with the match and a linkOpen it, or save anyway
0.75 to 0.92A quiet note: "Some similar items exist"Look, or ignore
Below 0.75Nothing shown. Still written to the log.Nothing

These thresholds are a starting guess, not a result. They get set properly during the two-week silent run on real traffic. At 0.92 the current alert rate is 33%, which is high — expect to raise it.

Always explain why. Show the reason, not the number: "names 97% alike · same manufacturer · both 50 mL". It comes free from the component scores and does more for adoption than any accuracy improvement.

Never block a save

The check warns; it never throws. 79 items in your system are all named "electrical installation at mrna lab" — they are not mistakes, they are CAPEX service entries, one per purchase order, and they are correct. Blocking duplicate saves would break a working business process on day one.

Non-stock items are skipped entirely, which removes that whole class of false warning with one line before any scoring happens. The whole check is wrapped in error handling that logs and returns nothing: a duplicate checker must never be the reason somebody cannot create an item.

10Logging every check

What we do. Every check writes one row to Item Match Log — including the silent ones nobody sees: what the user typed, the top 5 matches with scores and cancel reasons, which band it fell into, what the user did next (used the existing item / created anyway / gave up), why they created anyway (different size / different grade / genuinely new / service line), how long it took, and which version of the engine ran.

The two highlighted items are real human judgements on real pairs, captured for free. Three months of them is better training data than any amount of hand-labelling, and it is the only source of labels free from the Cat No leakage problem in section 6. Build it on day one, even though nothing reads it yet.

One thing to design around: users only judge the pairs we chose to show them, so we log the full top 5 including the hidden ones and occasionally review a random sample of those hidden pairs.

Why precision is the headline, not recall. A missed duplicate costs one extra row in the catalogue. A wrong warning teaches the user the tool is unreliable; after three of those they click past every warning forever, including the correct ones. Recall can improve for a year — trust does not come back.

The method. Build the test harness before tuning anything, or you are guessing. Replay history in date order for a free accuracy estimate at full scale. Run silently for two weeks before any user sees a warning. And never test on the training data — no exceptions.

12The data, and how we split it

We work from an Excel export, not a database backup — no fresh backup was available. Item.xlsx holds 25,590 items and 56 columns and is never modified; a working copy is taken before any processing.

What this costs us

The export has no creation date column, so the single most important question — are items still being created? — cannot be answered from this file. Action needed: re-export with the Created On column. It is one column, and it decides whether half this plan is worth building.

The split: 70 / 15 / 15, by product group, not by row.

A product group is a connected set of rows linked by Cat No (4,977 merges), identical Item Name (4,256) or Old Item Code (197) — giving 18,848 product groups from 25,590 items, of which 4,408 hold more than one item.

Why not shuffle rows and split? Leakage. The same product lands in both train and test; the model sees Glycine 500g in training and Glycine 500g. in testing, scores brilliantly, and fails in production.

product groups spanning more than one split : 0   OK
identical names split across sides          : 0   OK      (random_state = 42)

Settings that go with it: 4 non-duplicates per duplicate, drawn from name-similar candidates rather than random pairs (random pairs are too easy and teach nothing); remove Cat No junk first, or 14,814 fake pairs enter the split; and Cat No stays out of the clues, because it made the labels.

13How an Item Code is built

Worked out from the data, not from documentation.

RDCN  02  03  0516        PREFIX + CC(2) + SS(2) + NNNN(4)
 |     |   |    +---- serial number -- MEANINGLESS, discard it
 |     |   +--------- sub-category
 |     +------------- category
 +------------------- division / type prefix

Digits 1–4 predict Item Group 99.9% of the time and Item Child Group 99.3%. Digits 7–8 predict the child group only 37.4% — that is the serial, and it means nothing. Confirmed from the other direction too: inside every category the serial runs 0001, 0002, 0003 with no gaps, in 100% of the 154 groups tested.

But only 47% of items use this scheme.

ShapeItemsShareExampleCategory?
AAAA9999999913,90654.3%RDCN02030516Yes
A&A999998,33432.6%R&D08518No
AAAAA-99992,84111.1%CAPEX-02961No
AA/9999995002.0%RM/000707No

The root cause, visible in the codes themselves

RDCN… is the R&D division; CN… is Manufacturing. Same categories, separate numbering. The same product bought by two divisions gets two unrelated codes by design — and R&D08518 encodes no category at all, so another 32.6% carry no structure.

This is why 92% of duplicate groups span more than one code prefix. The duplicate problem is built into the numbering system. It is not caused by careless users.

Three rules follow. (1) Never text-match an Item Code — RDCN02030516 and RDCN02030517 are 92% similar as strings and are unrelated products; treating codes as text would be a disaster. (2) Parse it instead — prefix, category, sub-category, serial — and throw the serial away. (3) The code's category beats the field, because 9.6% of code-groups have an Item Child Group that disagrees with their own code; the code is set at creation, the field gets edited later.

And a useful signal falls out: same category but a different division prefix is evidence of duplication, not evidence against it.

The correction on Reference Old Item Code, and the lesson

We previously kept it because its separation was the highest of any field, +79.3. The ablation shows it changes zero decisions: it is filled on only 6.0% of items, both sides of a pair have it in about 4% of cases, and in those few cases the name score had already decided the answer.

Separation ranks a field's quality. Ablation ranks its usefulness. For a keep-or-drop decision, ablation is the one that counts.

Description — major for display, never scored

When the panel says "this item may already exist", a name alone is often not enough — the user needs to see what the existing item actually is. That makes Description actionable, and it goes into the Item Match Log so later review has full context. But five scoring designs were tested and none beat ignoring it:

15The three code files

All three live in item_duplicate_check/core/ and are pure Python — no Frappe import, no database — so they run and test in milliseconds without a site. Each carries a long header comment explaining what it does and why.

normalize.py — make two names comparable

"Nunc(tm) 96-Well Plate "   ->  "nunc 96well plate"
"nunc 96 well plate."       ->  "nunc 96well plate"

The ten rules from section 2, in a fixed order.

A bug the self-test caught

Trademark stripping originally ran after NFKC. But NFKC expands ™ into the two letters TM, which then glue onto the word in front: "Nunc(tm) 96-Well Plate" → "nunctm 96well plate". Moving the strip before NFKC fixed it. Left alone it would have silently broken matching for the 12.7% of names carrying a trademark symbol.

specs.py — block matches between look-alikes

The four checks from section 3, cheapest first, each returning a reason or nothing. Two rules stop it over-firing:

  • Abstention — a check only fires when both names have something to compare. Otherwise Paraformaldehyde could never match Paraformaldehyde for synthesis, and that class of match is one of the most valuable we have.
  • Subset, not equality — within a shared measurement, if one side's values are contained in the other's, nothing actually disagrees.
{mass 500}             vs {mass 1000}       -> CANCEL   neither contains the other
{length 0.22um, 33mm}  vs {length 0.22um}   -> ALLOW    one name is just fuller

The second case is real: Syringe Filter Unit, 0.22 µm, PVDF, 33 mm and Millex filter unit (0.22 um) are the same product. An earlier version compared sets for equality and wrongly cancelled it.

Every cancel returns why — e.g. "size: mass [500.0] vs [1000.0]" — shown to the user and written to Item Match Log, so a human can later judge whether the rule was right. That log is how this file gets improved.

itemcode.py — read the code, discard the serial

Parses all four shapes from section 13 and sets has_category so callers know when the category is real. same_category_different_division() returns true when two codes share a category but sit under different divisions — the duplication signal.

The open question that blocks half the plan: are items still being created?

On site_local, new items stopped in February 2026, while Stock Entries and Material Requests continue to October 2026. Before February the site created about 708 items a month — roughly 700 real decisions in three months, which is plenty. After February it is close to zero.

If yes — build everything, including the live panel and the model. If no — skip the live panel and the model, and focus on cleaning the 7,781 items already caught in Cat No clashes. The safety rules are needed either way.

This cannot be answered from Item.xlsx, because the export has no creation date column.

Suggested order of work

  2. Write tests/test_specs.py — move the 13 self-test pairs out of the __main__ block into a real test file. This document already calls it the living rulebook, but the file does not exist yet.

  6. Then the scorer, the API, the hooks and the panel.
